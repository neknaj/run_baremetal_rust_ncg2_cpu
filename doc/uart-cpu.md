# UART ブート用 CPU の命令フェッチ

`::rv64::uart-firmware-machine` は物理 PC を `0x0` に初期化し、ブート ROM と書き込み可能な RAM から命令を取得する。アプリは `[0x10000, 0x52000)` の4バイト境界で実行できる。命令を取得できない PC では停止信号 `stopped` が立つ。ROM の未使用語も不正命令として停止する。[ブート ROM の配置と受信プロトコル](uart-boot.md)

## PC とメモリポート

既存の実行部には物理 PC から `0x10000` を引いた相対 PC を渡し、更新先に `0x10000` を足す。いずれも64ビットの演算である。したがって、`AUIPC` が加算に使う値、`JAL` と `JALR` のリンク値、`JALR` の飛び先は物理アドレスになる。`commit` と同じ tick の `pc` は実行済み命令のアドレスで、次の tick に更新先が現れる。

`bus-address` と `read-data` は1つのポートを共有する。`issue` は初期化時と命令を完了したあとに立つ CPU 内部信号である。

| 時点 | ポートの動作 |
| --- | --- |
| `issue + 7` | フェッチのアドレスが確定する。PC の下位3ビットを0にし、命令のある64ビット語を読む。 |
| `issue + 64` | RAM の語を `read-data` に確定させる期限。この値を命令の取り込みまで安定させる。 |
| `issue + 72` | 選択済みの32ビット命令と有効ビットをラッチに取り込む。次のフェッチまで保持する。 |
| `issue + 79` | ポートは実行部のデータアドレスを選ぶ。このアドレスはオペランドが確定してから決まる。 |

RAM の語に対する応答時間はバスアドレスの確定から57 tick 以内とする。PC のビット2で語の下位32ビットか上位32ビットを選ぶ。ROM や範囲外をフェッチする期間にも PC に対応するアドレスを外部に送る。外部回路は読み出し自体に副作用を持たせず、`bus-write` に合わせて同じフレームの `bus-address` と `bus-write-data` を取り込む。RAM は同じ語の書き込みと読み出しが重なれば更新前の値を返す。[NCG2 の状態素子と read-first](https://neknaj.github.io/circuitgame2/docs/simulation.html)

## MMIO のアクセス幅

UART の語レジスタは表に示す命令と物理アドレスの組み合わせでアクセスできる。

| レジスタ | アドレス | 命令 |
| --- | --- | --- |
| STATUS | `0x200000` | `LD` |
| DATA | `0x200008` | `LD` |
| ACK | `0x200010` | `SD` |

語内の一部にアクセスするロードとストアは RAM に限る。MMIO のアドレスに1〜7を加えた位置や、表にない命令でアクセスした場合は、命令を無効とし、レジスタとメモリへの書き込みを抑止する。[UART の語レジスタ](uart-boot-mmio.md)

## 検証

SMT 検証器はPC の変換と RAM フェッチの実 NOR を展開する。64ビットの加減算、フェッチ可能な範囲と整列、語内の選択を独立したビットベクトル式と照合する。既存の命令実行部と組み合わせ、`AUIPC`・`JAL`・`JALR` の物理アドレスでの結果と、飛び先が4バイト境界を外れた場合の挙動も照合する。

命令全体の検証器は旧2プロファイルと UART プロファイルをそれぞれ展開する。有効判定、次の PC、レジスタやメモリへの書き込み要求を、プロファイルごとの独立したアドレス仕様と照合する。UART では LD と SD の許可と、部分アクセスや別アドレスから ACK を消費できないことも照合する。

VM のテストはブート ROM に UART の受信語を供給し、書き込んだ実 RAM からアプリを実行する。同じ語を更新する tick では更新前の値を確認し、アプリに移ったあとは連続した PC とレジスタ書き込み値を照合する。テスト用の UART は語インターフェースで代用し、RAM は先頭の4語を扱う。

```sh
host=$(rustc +1.99.1 -vV | sed -n 's/^host: //p')
cargo +1.99.1 run --quiet --locked --manifest-path verification/Cargo.toml \
  --target "$host" --example verify_uart_pc | z3 -in
for profile in firmware-dispatch firmware-dispatch-core firmware-dispatch-uart; do
  cargo +1.99.1 run --quiet --locked --manifest-path verification/Cargo.toml \
    --target "$host" --bin ncg2-rv64-arithmetic-proof -- "$profile" | z3 -in
done
cargo +1.99.1 test --locked --manifest-path verification/Cargo.toml \
  --target "$host" --test uart_entry
```

## RAM 書き込み前のアドレス保持

`verify_uart_store` は `uart-boot.toml` の入口を階層展開する。バスアドレス、書き込み許可、RAM に入る書き込みデータから、ラッチ出力と CPU に戻るデータ応答まで実 NOR の配線をたどる。公開 PC の配線を特定し、命令33ビット、オペランド64ビット、フェッチ選択1ビットの各ラッチを照合する。

| 観測先 | 入力ごとの最長 NOR 経路 |
| --- | --- |
| バスアドレス | 命令479、`rs1` 465、PC 4、フェッチ選択4、観測用アドレス16 |
| dispatch の書き込み許可 | 命令502、`rs1` 490、`rs2` 70、PC 34、フェッチ有効4 |
| 退役の有効性 | 命令500、`rs1` 488、`rs2` 68、PC 32、フェッチ有効2 |
| 乗算の判定 | 命令14 |
| 書き込みデータ | データ応答から8 |

データ応答からアドレスと書き込み許可への組み合わせ経路はない。データ応答は部分書き込みの旧語と、次に取り込む命令の一部になる。

ラッチ群の値を固定し、フェッチ選択を解除した状態では、dispatch が書き込みを許した命令は自然整列した SD・SB・SH・SW のいずれかになる。各ストアのバスアドレスは任意の tick ごとの観測用アドレスに対して、`rs1 + 符号拡張した S 即値` を8バイト境界へ切り下げた値と一致する。検証器は最長16段の観測用アドレスの経路を tick ごとに展開し、非選択側の値を任意にしたまま照合する。固定した入力の SD が許可される照合結果は `sat`、違反を探す照合結果は `unsat` となる。

```sh
set -e
host=$(rustc +1.99.1 -vV | sed -n 's/^host: //p')
mkdir -p target/verification
model=target/verification/uart-store.smt2
cargo +1.99.1 run --quiet --locked --manifest-path verification/Cargo.toml \
  --target "$host" --example verify_uart_store > "$model"
test "$(z3 -smt2 "$model")" = "$(printf 'sat\nunsat')"
```

検証器は `issue` から命令・オペランドの取り込み、フェッチ選択、通常の退役要求までの制御配線も照合する。公開 `commit` と `bus-write` は同じ退役信号を使う。乗算開始と通常の退役は、取り込んだ命令だけで決まる同じ判定信号を反対の極性で読む。読み取る tick は経路によって異なるが、命令が保持されれば判定は `i+87` までに確定し、どちらが読み取る時点でも同じ値になる。

初期化後に単独の `issue` パルスが tick `i` に入ると、照合した遅延から命令、`rs1`、`rs2` がそれぞれ `i+73`、`i+97`、`i+145` に取り込まれ、フェッチ選択は `i+75` に解除される。取り込んだ値と PC が次の書き込みまで保持される場合、ストアのアドレスは `i+562` から、書き込み許可は `i+587` から確定する。通常の退役経路でストアが `i+1033` に書き込む場合は、その tick を含む32 tick の全てでアドレスが一致する。

リセット直後と連続する命令枠で上の保持条件が成立することは、CPU 全履歴の証明に残る。実行中のアドレス保持は結合試験でも観測する。[RAM の要求と結合試験](uart-boot.md)

## 乗算完了後の反復停止

検証器は `done` と64ビットのラウンドマークが同じ許可で取り込まれることを実配線で照合する。初期化するとマークは `1`、`done` は0になる。初期化後はマークが1ビットずつ左に移り、更新前にマークのビット63が1なら `done` が立つ。次のマークと完了値はオペランドや積から独立している。組み合わせ経路の最長は実行状態から5段、マークから4段である。Verus はこの更新規則の帰納証明で、初期化後の64回目の取り込みで初めて `done` が1になることを示す。

実配線をたどると、最後の取り込みを tick `c`、状態素子の値を各 tick の終わりの値としたとき、次の制約が得られる。

- `done` が `t` から `t+1` に変わるには `t` の `capture` が必要になる。
- `t` で取り込むには `t-3` の開始要求か `t-518` の取り込みが必要になる。後者には `t-8` に実行中で `t-9` の `done` が0という条件もある。
- `t` で完了を通知するには、`t-6` の `done` が0、`t-5` の `done` が1でなければならない。

`verification/uart_multiply_control.rs` は単独の開始要求が効く時刻を `a` とし、その直前518 tick に取り込みがない場合を扱う。追加の開始要求が効くまで、取り込みが起こり得るのは `a` から518 tick の整数倍だけ進んだ時刻である。従って完了を確定する取り込み `c` の直前517 tick に別の取り込みはない。

初回の乗算では Core のリセット契約により各ラッチと NOR の出力が tick 0 に0となる。負の tick の信号は0で補う。実配線の初期化遅延は `capture` を tick 2 まで、反復と完了通知を tick 4 まで抑える。`done` の反転ゲートは tick 1 から反転値を返す。この起動条件を含む時刻式から、Verus で取り込み、`done` の保持、完了通知に関する上の3条件を導く。

開始要求がまだ効かない間は取り込みと完了通知が発生せず、`done` は0のままとなる。このため最初の乗算の直前518 tick に取り込みがないことも示せる。

取り込みと完了通知は、対応する時刻式の条件を満たすと発生する。開始要求が tick `s` に立てば `s+3` に取り込み、`s+11` に `running` が立つ。その後は完了通知が `running` のラッチに届くまで1を保つ。取り込みを tick `r` とすると、`r+509` の `done` が0で `r+510` の `running` が1なら、`r+518` に次の取り込みが発生する。Verus でこの反復条件を示した。

`c+1` に `done` が1なら、古い取り込みが最初に反復を起こし得る `c+518` でも `done` が保持されている。Verus ではこの間隔と保持から、次の開始要求が効くまで取り込みが発生せず、`c+7` 以降もその乗算の重複通知が出ないことを示す。次の開始要求が `c+519` 以降に効く場合は、その直前518 tick にも取り込みがなく、同じ証明を次の乗算に適用できる。

CPU 内部では退役通知から `commit` まで6 tick、`commit` から次の `issue` まで3 tick、`issue` から乗算の開始要求まで1,027 tick かかる。現在の命令枠が tick `i` に始まり、`i−8` から `c+5` まで別の退役通知がなければ、次の開始要求は `c+1042` 以降にしか出ない。要求が取り込みに効くのはさらに3 tick 後である。Verus ではこの間隔を上の停止条件と組み合わせ、`c+1045` の直前まで古い反復が発生しないことを示す。

```sh
verus --no-cheating --crate-type lib verification/uart_multiply_control.rs
```

開始要求を tick `s` とする。開始前に反復の遅延列が空で、`s−3` から `s+5` まで `running` が0であり、実行中に別の開始要求が来ない場合を Verus で証明した。初回の取り込みは `s+3`、続く64回は518 tick 間隔で発生する。64回目は `s+33155` で、その1 tick 後に乗算の初期化以来初めて `done` が立ち、`s+33161` に最初の完了通知が出る。マークの初期化とシフトが参照する `running` の時刻には1 tick の差があり、証明ではそれぞれの値を確認する。

CPU の命令枠に適用するときは、tick `i` の `issue` が `i+1027` に乗算を開始し、同じ時刻の通常完了を抑えることを使う。開始前の取り込みと `running` に関する上の条件に加え、直前1,035 tick に別の `issue` がなく、`i−8` から `i+1026` まで乗算完了通知がない場合を扱う。遅延配線を逆にたどると早すぎる `issue` には早すぎる完了通知が必要になる。通常完了は直前の空き区間と現在の命令種別から、乗算完了はラウンドの時刻式から排除できる。新しい `issue` は `i+34197` より前には発生せず、乗算は `i+34188` に完了を通知する。

完了通知を tick `f=i+34188` とすると、`f+3` で命令が有効なら `commit` が `f+6`、次の `issue` が `f+9` に立つ。次の乗算の最速開始時刻は `f+1036` である。Verus は前の乗算の取り込みが `f+1038` まで、重複の完了通知が `f+1045` まで発生せず、`running` は `f+3` から `f+1046` まで0になることも示す。これらの区間は、続けて乗算命令を実行する場合に必要な開始前の静穏区間を含む。

通常命令の枠では、tick `i+1027` に乗算を開始しない。早すぎる退役には、直前の空き区間に別の `issue` があるか、過去の乗算の完了通知が残っている必要がある。どちらもなければ次の `issue` は `i+1036` より前に発生しない。通常完了が `i+1027` に出て `i+1030` に命令が有効なら、`i+1036` に次の `issue` が立つ。乗算器は次の開始候補まで取り込みを発生させず、実行状態と完了通知も0を保つ。

Verus の `multiplier_window_ready` は次の枠に渡す `issue`、完了通知、取り込み、実行状態の静穏区間をまとめる。最初の `issue` は起動用パルスを受けて tick 4 に立つ。乗算の開始要求は早くても tick 1031 であり、最初の枠は静穏区間の条件を満たす。通常命令と乗算の両方で、この条件を満たす枠は次の枠にも同じ条件を引き継ぐ。

退役の有効性は保持した PC、命令とフェッチ有効ビット、2つのオペランドだけで決まり、観測用アドレス、RAM のデータ応答、積の変化には直接依存しない。PC を枠の開始時から保持し、命令とオペランドも取り込み後に保持する場合、命令種別は `i+87`、有効性は `i+585` までに確定する。両方とも乗算開始が参照する `i+1022` より前である。命令の分類を使わずに `i+1036` より前の次の `issue` を排除することも Verus で示した。

実配線から個々の時刻式を導く部分は、構造検査とラッチ・NOR の更新規則に基づく。PC と取り込んだ値が退役まで保持されることを時系列の定理につなぐ作業が残る。
